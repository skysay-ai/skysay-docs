A carrier reports a call answered the moment it starts carrying audio. That is
true of a person picking up, and equally true of a ringback replacement tune, a
hold-music loop, or a line that answers into silence. So "answered" on its own
cannot tell you whether anybody was there.

Every answered call therefore carries two separate facts:

- its **status**, which says the transport answered, and
- its **`answer_classification`**, which says what was heard afterwards.

## What the classification says

| Value | Meaning |
| --- | --- |
| `human` | a person was heard |
| `non_human_audio` | continuous music or tones held the line and nothing a person did was ever heard |
| `silent` | the line answered and nothing at all was heard |
| `unknown` | detection ran and reached no conclusion within its window |
| `""` | no verdict was reported at all |

The last two are not the same thing, and the difference is worth keeping.
`unknown` means detection ran and could not say. The empty string means nothing
was reported: the call was placed before this field existed, the agent has
collection switched off, or the call never carried media.

`reason_detail` qualifies the classification and nothing else:

| Value | Appears with |
| --- | --- |
| `caller_tune` | `non_human_audio` |
| `hold_music` | `non_human_audio` |
| `no_audio` | `silent` |
| `""` | every other classification |

It is not `ended_reason`. That field says why the call ended; this pair says
what was heard when it started. A call can carry both.

## Where the fields appear

Both fields are on the call resource returned by `GET /v1/calls` and
`GET /v1/calls/{call_id}`, on each call in
[call group results](/docs/post-call-results), and in the `call.completed`
webhook body. They are also on the call rows in your workspace.

```json
{
  "call_id": "call_...",
  "status": "completed",
  "answer_classification": "non_human_audio",
  "reason_detail": "hold_music"
}
```

That is a call that ran its course against hold music. Whether a call like it
is ended early is the subject of the next two sections, and it depends on one
per-agent setting.

## What counts as a person

A person is heard when speech starts and then stops. Concretely, either a burst
of speech-shaped audio that is followed by a pause, or a recognised word whose
audio has come to a stop. The pause is the part that matters: it is what
separates somebody saying "hello" from a recording that never breaks.

The reverse verdict is deliberately harder to reach. Skysay only calls audio
non-human when it runs continuously for several seconds with no pause in it, its
shape lacks the rhythm of speech, and no word is recognised in that window.
Anything short of all three is `unknown`.

That narrowness is on purpose, and it has a stated cost in both directions:

- **A recorded announcement is treated as a person.** Announcements and menu
  prompts have pauses in them, so they read as `human` or `unknown` and are left
  alone. Recognising a voicemail box is a separate detector with its own
  setting: see [Voicemail detection](/docs/voicemail-detection).
- **Somebody talking over music that never stops is missed.** Their words never
  land in a pause, so they are not counted, and the call is classified on the
  audio's shape alone.

Detection runs on the audio itself, in every language. It does not depend on a
transcript being available, and it never stores audio: only the verdict, its
score and the timings are recorded.

## The ending it is paired with

`ended_reason` has a value, `no_human_after_answer`, for a call the platform
ended because only non-human audio was ever heard after pickup. A call that ends
that way carries `answer_classification` `non_human_audio` and the detail naming
which kind, so the reason says that nobody was there and the classification says
what was heard instead.

An agent set to `end_call` ends a call this way in two situations and no others.
An agent left on `shadow`, which is every agent that has not been changed, still
ends nothing.

**A flat, unbroken tone or tune.** The audio runs continuously with no pause in
it, its shape lacks the rhythm of speech, and no word is recognised in the
window. That is the `non_human_audio` verdict described above, and it ends the
call on the same forty-five-second clock as the rule below.

**Nobody could have replied.** The far end holds the line for twenty seconds
without once leaving a gap of a second, so there has been no moment in which
anybody could have said anything back. This rule does not ask what the audio
sounds like, and that is the whole point of it: the caller tunes that prompted
this work are songs. A singer's voice has the rhythm of speech because it is
speech, and a recogniser turns the lyrics into words. What separates them from a
conversation is not how they sound. It is that a conversation alternates and
they never do.

A person stops the second rule by pausing, which anybody talking to somebody
else does within a second or two. The pause is the release, so nothing has to
recognise them first and the call simply carries on. They are not greeted again
and the call is not restarted; the agent picks up from where it is.

Neither rule ends a call in its first forty-five seconds. Both silence the
agent the moment they stand, and a pause before that point releases the rule
and the silence together.

On the four caller tunes measured below, that grace period never came into it.
A song stops between phrases and between tracks, so the far end keeps yielding
the floor and starting again; each of those calls produces between twenty-two
and thirty-three separate runs of audio. The first unbroken twenty seconds
does not complete until between fifty-one and seventy-five seconds in, long
after the forty-five is up, so each call goes quiet and ends on the same tick.

While either rule is standing, the agent stops speaking from its next turn
onward. The sentence already playing is not cut off. If the far end turns out to
be a person, the agent's voice comes back on the same pause that keeps the call
alive.

Silence and the ending are the whole of what `end_call` does. It does not hold
the call's own figures back from the agent. Withholding them until a person had
been recognised was built alongside this and removed before release, because it
did not work: a caller tune stops between phrases and between tracks, so the
signal meant to say "somebody is there" is produced by the music itself within
seconds. The figures are also part of the agent's setup instructions from before
the phone is picked up, so holding back what it is handed mid-call was never a
guarantee in any case.

### Why twenty seconds, and what it catches

Measured on every completed call of the batch that prompted this work:
seventeen calls, four of them answered by a caller tune, replayed through the
same voice-activity detection a live call runs on.

| | Longest unbroken far-end hold |
| --- | --- |
| The four caller tunes | 24.7 s at least, each |
| Every call that was not one | 8.3 s at most |

Twenty seconds sits between the two, and nearer the tunes than the margin
suggests: it is more than twice the longest hold any of the other thirteen
calls produced. All four tunes are ended and none of the thirteen is touched.

The side of that gap the line sits on is a real choice, not a rounding. A
person who holds the floor for twenty unbroken seconds, never once leaving a
gap of a second, is silenced and then ended. Nobody in this batch came within
eleven seconds of that, but seventeen calls in one language is not a promise
about every caller. Run an agent on `shadow` first and read what it records
for your own traffic before you move it to `end_call`.

Two of the thirteen are only seconds long and carry nothing that says what
answered them, so they are labelled as neither; they are counted with the
thirteen because the rule leaves them alone either way.

One more limit worth stating. A real person on a call that already triggered
the rule is spoken to again as soon as they pause, because the pause is the
release; the call is not restarted and they are not greeted a second time.

A call that ends this way is reported as not connected:

- it is excluded from a campaign's connect rate, and from talk time;
- its campaign disposition is `no_answer`, because no person was reached, so the
  contact is dialled again under your campaign's existing backoff rather than
  being treated as a conversation that happened;
- its `termination_cause` stays `connected`, because that field describes the
  transport and the transport genuinely did answer. The two are separate
  questions and the fields answer one each;
- carrier minutes up to the point it ends are real and are billed as usual.

## Personal facts wait for a person

On an outbound call that carries a `call_context`, the AI model is not given
the call's personal facts until a person has answered the agent. That covers the contact's name, the amount and the reference, and
anything else from `call_context` that Skysay hands the model. Voicemail, hold
music, a carrier announcement or silence never get them, however long the
call runs.

- Until a person is heard, the agent greets and asks who it is speaking with.
  It does not say a name, an amount or a reference.
- The facts are handed to the model mid-call once three things are true.
  Answer detection has heard a person. That person has answered the agent
  twice in a row: each time they mostly listened while the agent spoke and
  replied after it finished. And what they said in those two replies gives no
  sign of a machine.
- A reply gives a sign of a machine when it contains voicemail or phone-menu
  wording (for example "leave a message", "after the tone", "press one" or
  "is not available", in the call's language or English), when it repeats
  something already said on the call, or when voicemail detection has
  classified the call as a mailbox, a menu or a call screener. A recording
  whose pauses happen to line up with the agent can look like a person by
  timing alone; this is what tells them apart. Speech that could not be
  transcribed counts as no reply, so the facts stay held until a reply is.
- A recorded announcement or a sung hold track that talks straight over the
  agent never releases anything.
- On a normal pickup the facts follow the caller's second reply, typically
  15 to 25 seconds in. Someone who talks over the greeting gets them after
  answering the agent's next two lines. Someone who says "hello" and then
  waits in silence does not get them at all, and the agent carries on without
  the name. There is no timer that releases them anyway.
- This applies to every conversation engine, and to the model that routes a
  [workflow](/docs/agent-workflows) caller's replies.
- Inbound calls and browser tests have the facts from the start. The caller
  dialed in, or you are testing your own agent, so there is no answer to
  classify.

What Skysay does not hold back is content you wrote yourself. If your agent's
prompt, a literal `first_message`, or the response of your own integration or
webhook tool contains the contact's name, the model has it from the moment
that text reaches it.

## Choose what an agent collects

`answer_detection.non_human_audio` is set per agent, in the **Answer detection**
card of the agent editor or through
`PATCH /v1/agents/{agent_id}/voice-stack`.

| Value | What it does |
| --- | --- |
| `shadow` | Records what was heard on every answered call and changes nothing the caller experiences. |
| `end_call` | Acts on the verdict. The agent goes quiet, and the call is ended with `no_human_after_answer`. |
| `off` | Collects nothing that is reported. Calls carry no answer classification at all. On an outbound call that carries a `call_context`, Skysay still listens for a person, only to decide when the call's facts may reach the model; that verdict is not stored or sent, and nothing else about the call changes. [Voicemail detection](/docs/voicemail-detection) set to `off` is treated the same way. |

`shadow` is what an agent with no stored value gets, and it is the only value
that can measure how often the verdict would have been wrong without being able
to end anything. Move an agent to `end_call` once you have looked at what
`shadow` recorded for it.

```bash
curl -X PATCH https://api.skysay.ai/v1/agents/agt_123/voice-stack \
  -H "Authorization: Bearer $SKYSAY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"answer_detection": {"non_human_audio": "off"}}'
```

### Choosing a value is not the same as leaving it alone

This setting deliberately behaves differently from the other per-agent tuning
sections. Everywhere else, saving a value equal to the current default is the
same as saving nothing. Here it is not:

- an **absent** `answer_detection` key means "follow the platform default",
  which is `shadow` today and is expected to change once the detector has been
  measured;
- an **explicit** value is stored as you sent it, including `shadow`, and the
  agent keeps it when the platform default moves.

So if you want an agent to observe and never do anything else, send `shadow`
rather than leaving the section out. The editor makes the same distinction: the
first choice is Platform default, and Shadow beside it is the explicit one.

The setting applies when a call starts; saving it never changes a call already
in progress.

`shadow` is the platform default on purpose, and `end_call` is a choice you
make per agent rather than something that arrives underneath you.
