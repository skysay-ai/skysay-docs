An agent workflow turns an open-ended voice agent into a governed conversation:
a graph of typed steps with named routes, hard limits, and evidence for every
turn. You build the graph visually — or describe it in plain language and let
AI draft it — while Skysay continuously compiles it into a versioned,
server-validated runtime contract. The model phrases nothing on its own
authority: it chooses between the routes you declared, and the server applies
the transition.

## The canvas

Open any agent and choose **Workflow**. If the agent has no workflow yet you
can start from a template (Payment reminder, Customer support, Receptionist,
Appointment booking),
a blank canvas, or a natural-language brief that AI turns into an editable
first draft. Creating a workflow creates only a private draft — no number is
attached, no tool authorized, no call placed, nothing published.

Each step is one governed unit:

| Step | What it does |
| --- | --- |
| **Ask** | Speaks a question and waits for the caller. |
| **Tell / Say** | Speaks approved information; may continue silently or end the turn. |
| **Read tool** | Runs, silently inside a turn, one of the AI agent's own tools (see [Tools on a workflow call](#tools-on-a-workflow-call)), or checks that the call carries the data the next lines need. Takes its error route when it cannot. |
| **Branch** | Chooses exactly one named route from the caller's answer. Cannot invent routes. |
| **Outcome** | Records a structured result or review candidate. |
| **Transfer** | Hands the live call to a configured destination, with a declared fallback. |
| **Send SMS** | Sends an authored text message to the number on the call, then continues. |
| **End** | Speaks the farewell and closes the session. |

Routes carry the labels you write ("Can pay", "Dispute"), and those labels are
what the model reasons over; the compiled contract keeps stable ids underneath
so renaming a label never changes execution identity. Moving nodes, zooming,
or collapsing groups changes layout metadata only — the compiled contract is
proven independent of everything visual.

**Global interrupts** — wrong party, dispute, hardship, cease contact,
callback, human request, language change — are configured once on a separate
rail. They can preempt any ordinary step, and when a caller's utterance
matches more than one, the server picks the highest-precedence interrupt from
a fixed order; the model never decides precedence.

**A reply to a spoken line that leads straight to a branch** is decided once,
against that branch's routes and the global interrupts together. The dispute,
hardship, callback and human-request interrupts are weighed against your routes
as one choice: a route you wrote for the reply ("Already paid", "Has a
question", "Wants to leave a message") is taken when it fits what the caller
said better, so the branch you laid out answers them, and when none of your
routes fits, the interrupt applies as before. Wrong party, cease contact and
language change are always checked on their own and still preempt any route.
When a read tool or Send SMS step sits between the line and the branch, the
branch decides after that step, separately, as before.

Every semantic edit is also available from the form/list editor without
drag-and-drop, and edits autosave to the draft only. If someone else edits the
same draft, stale writes are refused with the current state rather than
silently overwritten — saving, publishing, and restoring all carry the
revision you reviewed.

### Payment reminder identity clarification

Both **Payment reminder** starter templates ask whether the caller is the
account holder before reading or speaking account details. When a delivered
reply is classified as **Unclear**, the workflow asks at most two clarification
questions. This route covers hesitation, fragments, and empty replies rather
than treating them as denial. If identity is still unconfirmed, it records
**Identity unconfirmed** and ends without a case read or a wrong-party outcome.

Wrong party requires explicit denial of being the intended person or a clear
wrong-person or wrong-number statement; missing confirmation alone is not
denial. Explicit wrong-party and cease-contact replies both end the call
immediately, but they are two different outcomes and the starter templates keep
them apart. A **wrong party** stops this call and leaves the number exactly
where it was. A **cease contact** stops this call and records that the caller
asked not to be contacted, for you to review. Nothing adds the number to your
[do-not-call register](/docs/campaigns#do-not-call-register) automatically --
a caller can say anything, so you decide whether a number goes on it, and the
numbers you add are honoured on every outbound path. Each outcome keeps its own
label, so an exported row or a review-inbox entry says which of the two
happened.

The starter templates used to label the cease-contact outcome "Asked not to be
contacted — call stopped, number added to the do-not-call register". Your
drafts carry "Asked not to be contacted — review" instead, and so does a draft
you restore from a version published with the old label, so publishing it again
does not bring the old claim back. The old text is recognised however it is
spaced or capitalised; a label you wrote yourself is kept as it is.

A reply to a **Tell / Say** line is judged together with that line as the
caller heard it, including the call's values it stated, so a short "no" to a
question the line asked — "Have you already paid it?" — is an answer, not a
denial of identity. Only that one line is added: the workflow's other steps,
the caller's earlier replies and any variable the line does not state never
reach the decision model. The values are included only when the model that
judges replies runs on the same provider as the agent's own model, so your
data reaches no provider the call was not already using. For any other
provider the line goes as you wrote it if it names no variable, and is left
out if it does.

Because the two mean different things, a workflow may not point both
interrupts at one outcome step, and validation refuses a draft that does. Both
outcomes are **review candidates** rather than automatic actions: neither writes
to your do-not-call register. Global interrupt precedence is unchanged.

Any draft whose wrong-party and cease-contact interrupts point at one existing
step was updated for you when this shipped -- drafts built from an earlier
starter template, and drafts where you wired that shared outcome yourself. The
cease-contact interrupt now lands on an outcome step of its own, with the id
`cease_contact_stop` (suffixed if your draft already uses that id), and the step
it used to share keeps its id and every other route that reached it, so nothing
you had wired is broken. A label you wrote yourself is kept as it is; only the
starter template's own wording was replaced. Versions you had already published
are immutable and were not touched -- the updated draft takes effect the next
time you publish. Without this your existing draft could not have been published
again, because the validation rules above refuse the shape it was in.

**If you send `base_revision`, re-read the draft first.** The repair is a write,
so it advances the draft's `revision`. A client holding a revision from before
the release -- an integrator that re-seeds a workflow on a schedule, for
instance -- gets `409` on its first `PATCH /v1/agents/{id}/workflow` or publish
after it. That is the ordinary someone-else-changed-this answer and the `409`
body carries the current draft under `current`, so reconciling against it is
enough; nothing is lost. `GET /v1/agents/{id}/workflow` returns the new revision
and the split draft together.

These routing instructions depend on the decision model interpreting the
reply correctly. An incorrect global interrupt decision still preempts local
clarification; synthetic tests do not prove speech-recognition or model accuracy.
This does not add a no-speech timer: silence that produces no transcript turn
does not advance the clarification steps.

Template updates do not rewrite existing drafts, custom workflows, or immutable
published versions. To adopt the clarification steps on an existing agent,
explicitly update its draft, test the new routes, and publish a new version.

## Validation, then testing, then publishing

### Reconcile before an edit or publish

An API client reads the current state with
`GET /v1/agents/{id}/workflow?version_limit=20&version_offset=0` before it
PATCHes or publishes. The `agents:read` response includes the editable
draft/revision, validation, safe canvas layout, active published-version
metadata, and a bounded newest-first version summary so the client can compare
what it intended to change. The draft comes back whole -- its `variables`
(normalized; if any declaration cannot be read, the whole `variables` block is
left out, and the draft's `validation` says why), each identity step's `matches` and every Send SMS step
-- so a client that reads, edits and writes the draft back keeps them. It is a pure read: no AI or provider call, compile,
repair, lazy creation, or other mutation occurs.

`workflow_state: "not_created"` is the explicit response for an existing agent
that has no draft. Create a workflow only with the write endpoint; the read
will never synthesize one.

Validation blocks testing and publishing on structural errors: dangling or
type-invalid targets, unreachable required steps, cycles with no exit, missing
interrupt targets, a wrong-party and a cease-contact interrupt sharing one
outcome step, tool or language incompatibilities, blank spoken text, missing
transfer destinations, a line that names a variable the workflow does not
declare, and a line or SMS that could say a
[protected variable](#protected-values) before the caller is confirmed
(`PROTECTED_BEFORE_CONFIRMATION`, naming the step). Warnings are separate and must
be explicitly acknowledged before publishing.

Four test modes run against the exact draft — its voice stack, knowledge,
tools, and workflow:

- **Talk** — a real-time microphone conversation in the browser, with the
  active step and traversed routes highlighted live. Microphone permission is
  requested only after you start.
- **Chat** — the same draft as text, with no microphone or voice cost. The
  reply you see is the step text you authored, filled in with your
  [test values](#testing-with-values); the decision model in use is
  always reported. (An agent without a flow has a Chat mode too, driven by
  its instructions rather than a flow; see [Test an agent](/docs/trial-calls).)
- **Simulations** — repeatable synthetic personas with expected outcomes,
  controlled tool mocks, pass rates, and step traces grouped by conversational
  turn.
- **Phone** — a controlled test call on an attached, eligible number. You arm
  a short-lived pin for one declared caller number and one attached number;
  while it is armed, calls from that caller run the pinned draft, and every
  other caller continues to reach the published workflow. Pins expire on a
  timer and after a bounded number of matches.

Draft tests can never execute unapproved mutation tools and never publish
anything implicitly. Runs record the exact pinned contract, each step, the
chosen route, tool status, and the policy reason for every transition — no
transcript secrets, no raw provider errors.

Publishing creates an immutable version. Ordinary callers move to it only when
you publish; drafts never affect live traffic. Restoring an old version copies
it into a new draft — history is never rewritten — and version history shows
what changed between versions.

## Call variables

A workflow speaks the data each call carries through
[call variables](/docs/call-variables): `{{balance_amount}}` in a line is
replaced with that call's value, with the same markers, sections and limits as
everywhere else. A workflow agent declares its variables **on the workflow**,
not in the agent's variables config:

```json
{
  "variables": {
    "version": 1,
    "fields": {
      "first_name": { "type": "string" },
      "balance_amount": { "type": "number", "protected": true, "requires": "confirmation" },
      "date_of_birth": { "type": "string", "format": "date:YYYY-MM-DD", "protected": true, "requires": "confirmation" }
    }
  }
}
```

`PATCH /v1/agents/{agent_id}/workflow` takes them as the draft's `variables`,
replacing the draft's; `null` removes them, and a save that leaves the key out
keeps them.

An agent whose publication already declares its own variables hands them to
its workflow when that workflow is published: in the same step the agent's own
declaration is cleared (its SMS templates, SMS mode and caller lookup stay) and
the agent is republished against the workflow's. The publish response lists
the cleared names the workflow declares in `variables_moved_to_workflow`, and
the cleared names no line used, which the workflow does not declare, in
`variables_dropped` (each an empty list when there are none). The cleared
declaration is kept, word for word, in the audit event
`agent.variables_moved_to_workflow` (`GET /v1/audit-events`), with the
`workflow_version`, the `moved` and `dropped` names and the
`cleared_variables`, so the handover can be seen and the declaration
recovered. If the agent's greeting,
its instructions or one of its SMS templates names a variable the workflow does
not declare, the publish is refused with `400 variables_config_invalid` and
nothing changes -- declare it on the workflow and publish again. The issue says
where: `UNDECLARED_VARIABLE` at the greeting or instructions, or the template
check's own code at `sms_templates.<id>.text.<language>`. They are checked when the workflow is published, with every line:
a line that names an undeclared variable, prints an optional one outside its
own `{{#name}}` section, or has a misspelled or unbalanced marker is a
validation error naming the step. In the dashboard they are on the workflow's
**Variables** tab.

Every `{{` in a line starts a marker. There is no way to write two literal
braces in a line: a `{{` that is not a valid marker is refused when the
workflow is published.

### Protected values

A variable marked `protected` is held back until the caller has shown they are
the right person — a balance, an account number, a date of birth. Until then it
is not spoken, not given to any model, not sent by SMS, and not sent to any
tool. The workflow is checked when you publish it: a line or SMS the caller
could reach before being confirmed that names a protected variable is refused
as `PROTECTED_BEFORE_CONFIRMATION`, naming the step, whichever way the call
reaches it — from the entry step, an interrupt or the fallback step.

A protected variable's `requires` says what releases it (`confirmation` by
default):

- **`confirmation`** — the caller confirms who they are. An **Ask** step marked
  `verifies_identity: true` names the routes that mean "yes, that's me" in
  `verified_routes`; taking one of them confirms the caller. This is a
  conversational check: it stops a wrong person who says so, not one who lies.
- **`knowledge_match`** — the caller states something only they know, and
  **the platform** compares it with a protected value the caller never heard.

For a `knowledge_match`, the identity step declares what to compare:

```json
{
  "id": "check_birthday", "type": "ask", "prompt": "What is your date of birth?",
  "verifies_identity": true, "verified_routes": ["matched"],
  "matches": { "field": "date_of_birth", "kind": "date", "on_mismatch": "not_matched" },
  "routes": [
    { "id": "matched", "label": "Gave their date of birth", "target": "explain_balance" },
    { "id": "not_matched", "label": "Did not match", "target": "identity_unconfirmed" }
  ]
}
```

- The decision model only **extracts** what the caller said; it never sees the
  stored value and never decides whether it matches.
- `kind` is how the two are compared: `number` (numerically), `digits` (for a
  field with `format: identifier`: spaces, hyphens and dots ignored), `casefold`
  (text, ignoring case) or `date` (for a field with a `date:` format, whatever
  way the caller said it).
- A match takes the step's one verified route and releases the fields. A
  mismatch, or an answer that cannot be read as the kind, takes `on_mismatch`,
  another of the step's own routes. When the caller gives no answer at all, the
  step is asked again, up to its visit limit, and then takes `on_mismatch`.
- A `requires: "confirmation"` field is released by either method; a
  `requires: "knowledge_match"` field only by a match.

Validation refuses a `matches` that is not on an identity **Ask** step with
exactly one verified route, that names a variable that is not protected, whose
`kind` does not fit the variable, or whose `on_mismatch` is not another route
of the same step (`INVALID_MATCHES`, `MATCHES_WITHOUT_VERIFICATION`,
`MATCH_VERIFIED_ROUTE_NOT_SINGLE`, `MATCH_FIELD_NOT_PROTECTED`,
`MATCH_KIND_INCOMPATIBLE`, `MATCH_MISMATCH_ROUTE_INVALID`).

The confirmation is recorded with the turn that confirmed it, and a protected
value is released only once that turn is stored: a line in the same turn,
after the confirming step, may say it.

### Read tool steps

A **Read tool** step declares a projection: the variable names the lines after
it rely on. On a call it checks that each of them has a value on this call —
nothing is fetched, and the step never reads a value out. If one is missing, the
read fails and the workflow takes the step's error route (the
case-unavailable outcome in the Payment reminder templates), so a line is
never spoken with part of the data missing. The run's step evidence records
the reason (`case_snapshot_missing`), never a value.

A **Read tool** step can also run one of the AI agent's own tools, such as its
knowledge base search or its calendar; see
[Tools on a workflow call](#tools-on-a-workflow-call).

### Several obligations on one account

A variable may be a **list** — one account, several loans — declared with its
item keys:

```json
"obligations": {
  "type": "list", "protected": true, "requires": "confirmation",
  "item": { "reference_id": "string", "overdue_amount": "string", "currency": "string", "due_date": "string" }
}
```

A list is spoken only through a **section**: the body between `{{#obligations}}`
and `{{/obligations}}` is repeated once per item, in order, with the item's own
keys in scope. Every word and punctuation mark a caller hears is still yours:

```text
Our records show the following on your account. {{#obligations}}For reference
{{#reference_id}} {{reference_id}}{{/reference_id}}, an overdue amount of
{{#overdue_amount}} {{overdue_amount}}{{/overdue_amount}}{{#currency}} {{currency}}{{/currency}}.
{{/obligations}}Are you able to take care of this today?
```

A list holds at most 16 items. The **Payment reminder from contact variables**
starter template is built on this: its one read tool (`read_contact_variables`)
checks `obligations`, its disclosing step is the section above, and on a
campaign call the values are the contact's own variables — no customer
endpoint.

### Send SMS steps

A **Send SMS** step sends its authored `text` to the number on the call — the
caller on an inbound call, the person called on an outbound one — then
continues to `next`. The text uses the call's variables like any line, and is
refused rather than sent with a gap. It must fit 6 segments with the values it
is sent with: that is checked when it is sent, and a message over it is not
sent -- the step records **SMS failed** (`OUTPUT_BUDGET_EXCEEDED`) and the call
continues. It may name a
protected variable only where the caller has been confirmed, which publishing
checks as for spoken lines. The message is sent after the turn that reached
the step is stored, once each time the step is reached. Talk and Chat record
the message and send nothing.

The call's **Identity checks and SMS steps** list shows each message's status:
**SMS sent**, **SMS failed**, or **SMS delivery unknown** when the SMS provider
may have accepted the message without confirming it. A message whose delivery
is unknown is never sent again, so the person cannot receive it twice. The
workflow does not wait for the result: a later line in the same turn should not
say the message has arrived.

### Testing with values

**Talk** and **Chat** render every line with the test values you give them
(`test_values`), exactly as a call admits them, and run identity steps too: a
comparison checks the caller's answer against the test value, and a missing
test value counts as a mismatch. Protected values are shown only after the
confirming step. An SMS step's message is recorded, not sent. In a scripted
simulation, taking the step's verified route counts as a match, and anything
else as a mismatch.

### Versions from before call variables

When your workspace moves to call variables, every workflow version published
before then keeps its number and shows as **Archived before call variables**
(status `archived_v2`). An archived version cannot run a call
(`workflow_binding_failed`) and cannot be restored.

Rerunning a simulation run from before the move:

- a run against the version that was active reruns on its migrated copy, which
  says the same words;
- a run against an older version is refused with `409` ("This run's workflow
  version predates call variables and could not be moved to them. Run the suite
  again.");
- a run against a draft from before the move is refused with `409` ("This run's
  draft predates call variables. Run the suite again against the current
  draft.").

The version that was active gets a new copy, numbered after the workflow's
highest version and moved to call variables. It becomes the active version and
shows with its origin, for example **v5 (migrated from v3)**; the API's version summary
carries the old number as `migrated_from_version` (null on every other
version). Your next publish takes the next number.

Restoring an archived version answers `409`, naming the copy to restore
instead ("Version 3 was moved to call variables as version 5. Restore that
version instead."), or saying the version predates call variables and was not
moved. To take calls on the current workflow, publish the draft, which
declares its variables.

## Tools on a workflow call

On a workflow call the AI agent's model is offered no tool of its own: the
workflow decides every turn, and its **Read tool** steps run the AI agent's
tools for it. A step can run one of these:

| Tool | What the step does | What a later line can say |
| --- | --- | --- |
| **Search the knowledge base** | Searches the knowledge bases attached to the AI agent for the caller's question and quotes the documents' own sentences that answer it. | `{{tool.knowledge_answer}}`: whole sentences of the documents, exactly as written and in the documents' language |
| **Check calendar availability** | Asks the AI agent's calendar for free times in the range the caller asked about. | `{{tool.available_times}}`: up to three offered times with their dates, said in the call's language with the calendar's time zone |
| **Book an appointment** | Books one of the offered times, and only after the caller says yes to the platform's read-back; see [Book an appointment](#book-an-appointment). | `{{tool.booking_when}}`, `{{tool.booking_length}}`, `{{tool.booking_name}}`, `{{tool.booking_email}}`: said by the read-back question; `{{tool.booking_needs}}` and `{{tool.booking_needs_email}}` when details are missing |
| **Integration action** | Runs one of the AI agent's Integration actions that read. An action classified as one that changes something is refused (`workflow_tool_not_read`), however the workflow declares it; the agent page shows it as **Changes data**. | `{{tool.<key>}}` for each result key you list: text or a number |

A tool runs only if the AI agent has it. Nothing is attached for you: the
knowledge search is there once you attach a knowledge base to the AI agent
([Knowledge Bases](/docs/knowledge-bases)), the calendar tools once you select
it on a calendar connection and choose **Enable booking**
([Calendar booking](/docs/calendar-booking)), and an Integration action once
you add it to the AI agent's tools. If the AI agent does not have the tool when the call runs, or the
tool fails, finds nothing or runs out of time, the step takes its error route.

### Choose a tool for a step

Select a **Read tool** step and open its **Tool** list. The tools the AI agent
has are grouped under **This AI agent's tools**; if there are none, the
inspector says what to attach first. For an Integration action, enter its
**Result keys**: one to eight top-level keys of the action's result, separated
by commas. A line says each one as `{{tool.<key>}}`; a value that is not text
or a number, or is missing, fails the step.

You do not write the tool's arguments. The platform works them out from what
the caller said: the question to search for, the time range to check, and, for
a booking, the chosen time, the caller's name, and the email address and any
answers the calendar's event type needs. If something is still missing, the
step takes its error route, and what the caller already gave is kept for the
next time the step runs.

Place a tool step where the caller has just answered, before the line that
speaks its result: after an **Ask**, or after a **Branch** that follows one. A
tool step reached after a spoken line of the same turn does not run and takes
its error route, because every line of a turn is said with one set of values;
validation warns about it (`AGENT_TOOL_AFTER_SPOKEN_LINE`).

### Speak a result

A step's results are values in the `tool.` namespace that later lines of the
workflow can say. They are optional, so a line says one inside its own section,
as with any optional [call variable](#call-variables):

```text
{{#tool.knowledge_answer}}{{tool.knowledge_answer}}{{/tool.knowledge_answer}} Is there anything else I can help with?
```

```text
{{#tool.available_times}}I have {{tool.available_times}}.{{/tool.available_times}} Which time would you like, and what name should I book it under?
```

With a calendar in `Europe/Tallinn`, the second line is said as "I have
Tuesday, November 3, 2026, 10:00 AM or 11:30 AM or Wednesday, November 4, 2026,
2:00 PM (Eastern European Time)." In another language the dates, times and
time zone follow that language's own conventions.

- A result is never a call variable. A contact, `call_context` or a campaign
  cannot supply it, and you do not declare it on the **Variables** tab.
- Only the workflow's spoken lines can say a result. A **Send SMS** step, the
  greeting and the instructions cannot name one; validation refuses a draft
  that does.
- A step that fails clears its earlier results, so a later line never says a
  previous answer as if it were this one.
- A knowledge answer is never text a model wrote. A model only picks which
  sentences of the retrieved passages answer the question; the platform checks
  that they are the document's exact words and says each whole sentence they
  come from. When nothing in the documents answers, the step takes its error
  route.
- A result is never cut short. A knowledge answer or a list of times over 300
  characters, an Integration value over 200 characters (600 for one action's
  values together), or a line that would grow past its limit with the result
  in it fails the step instead.

### Book an appointment

A booking writes to a real calendar, so a booking step has a second way out:
besides `next` and its error route, it has a **read-back question**
(`on_confirm`). The step's first request books nothing. It takes the call to
the read-back question, which says the date and time with the time zone, the
length, the caller's name, and whether and where a confirmation email goes,
then asks "Shall I book it?". In English:

```text
To confirm: an appointment on Tuesday, November 3, 2026, 10:00 AM (Eastern European Time), lasting 30 minutes, for Mari Tamm. No confirmation email will be sent. Shall I book it?
```

The question is the platform's own, in fixed wording you cannot edit, for
every language the workflow is published in: English, Estonian, German,
Spanish, French and Russian today. A workflow in another language cannot
publish a booking step. Select the booking step and choose **Add the read-back
question** to add it together with its one clarification. Its "No" route
starts at the booking step's error route and its "Wants a change" route at the
workflow's availability step; rewire them as you need.

The caller's answer to the read-back question decides what happens. Your route
labels play no part: the answer is taken as one of four fixed answers.

| The caller says | What happens |
| --- | --- |
| An explicit, unconditional yes | The booking step books exactly what was read back, then continues to `next`. |
| No | Nothing is booked; the call takes the **No** route. |
| A change ("yes, but at three") | Nothing is booked; the call takes the **Wants a change** route, and any later booking needs a new read-back and a new yes. |
| Something unclear ("I guess", "mm") | The call takes the **Unclear** route to the one clarification, which starts "Just to be sure", repeats the details and asks for a yes or a no. A second unclear answer counts as no. |

Silence, hanging up or an interruption never books. A yes that arrives within
a few seconds of the read-back, before it could have been heard and answered,
is not booked early: the read-back question is asked again. The platform never
asks the model that works out the booking details whether the caller agreed;
only the answer to the read-back question can.

The time the caller picks ("the second one") must be one of the times said in
the reply they are answering, in the language they heard it in. Otherwise the
booking step takes its error route rather than guess. A booking the calendar
refuses, or whose result at the provider is uncertain, also takes the error
route and is never reported as booked: word that line so it does not say the
appointment exists, and check the call's appointment in **Calls**.

When a booking request lacks an email address the calendar needs for its
invitation, or an answer to one of the calendar's own questions, the step takes
its error route and sets two values for that line: `{{tool.booking_needs}}`
lists the labels of the unanswered questions ("Reason for visit and Phone
number"), and `{{tool.booking_needs_email}}` is set when an email address is
needed. Say them inside sections, as the **Appointment booking**
template does:

```text
Sorry, I couldn't confirm a booking for that.{{#tool.booking_needs_email}} I also need your email address for the confirmation.{{/tool.booking_needs_email}}{{#tool.booking_needs}} I also need: {{tool.booking_needs}}.{{/tool.booking_needs}} Could you tell me again which time you'd like and the name for the booking?
```
 A line of
your own after a successful booking can say its details too, such as
`{{#tool.booking_when}}Your appointment on {{tool.booking_when}} is booked.{{/tool.booking_when}}`,
because they are the calendar's own read-back, never the model's. All the
other booking rules of [Calendar booking](/docs/calendar-booking) apply too,
such as at most two booking attempts per call.

Validation refuses a booking step without its read-back question
(`WRITE_TOOL_NEEDS_CONFIRMATION`), a read-back question whose wording was
changed (`READ_BACK_INCOMPLETE`), a booking step in a workflow language the
platform has no read-back for (`BOOKING_CONFIRMATION_LANGUAGE_UNSUPPORTED`),
and a read-back question with other routes or reachable from anywhere but its
booking step (`INVALID_CONFIRMS`).

Through the API, a tool of the AI agent's own is a `declared_tools` entry with
`"source": "agent"`. The knowledge search and availability are `read` tools
and the booking is a `write`, all three with an empty `projection`; an
Integration action is a `read` whose `projection` lists its result keys. The
booking step names its read-back question in `on_confirm`, and both questions
name the booking step in `confirms`:

```json
{
  "declared_tools": [
    { "name": "calendar_check_availability", "kind": "read", "source": "agent", "projection": [] },
    { "name": "calendar_book_appointment", "kind": "write", "source": "agent", "projection": [] }
  ],
  "steps": [
    { "id": "book_appointment", "type": "read_tool", "tool": "calendar_book_appointment",
      "next": "booked", "on_error": "booking_details_needed", "on_confirm": "confirm_booking" },
    { "id": "confirm_booking", "type": "ask", "confirms": "book_appointment", "prompt": "<the platform's read-back>",
      "routes": [
        { "id": "yes", "label": "Yes", "target": "book_appointment" },
        { "id": "no", "label": "No", "target": "declined" },
        { "id": "change", "label": "Wants a change", "target": "check_availability" },
        { "id": "unclear", "label": "Unclear", "target": "clarify_booking" }
      ] }
  ]
}
```

The clarification is a second `ask` that `confirms` the same booking step, with
the routes `yes`, `no` and `change` and no `unclear`. The read-back question
must have its `unclear` route, leading to that clarification; without it
publishing fails with `WRITE_TOOL_NEEDS_CONFIRMATION`. Validation also refuses an
agent tool declared with the wrong kind (`AGENT_TOOL_KIND_INVALID`,
`MUTATION_AUTHORITY_UNAVAILABLE`), a built-in with fixed results given a
`projection`, an Integration action given none or more than eight keys, or
AI agent tools that together give more than 64 results
(`AGENT_TOOL_RESULT_INVALID`), and a result given by two tools or a tool
declared twice (`AGENT_TOOL_RESULT_DUPLICATE`). It also refuses one of the AI
agent's own tools declared without `"source": "agent"`
(`AGENT_TOOL_NEEDS_SOURCE`): without it, a declared tool only checks that the
call carries variables of those names and runs nothing, so a booking step
would succeed without booking. This covers the knowledge search, both calendar
tools, and the built-ins a workflow has its own steps for.

### Starter templates with tools

- **Customer support** searches the AI agent's knowledge base and says the
  answer, or escalates when nothing is found.
- **Appointment booking** answers questions from the knowledge base, offers
  free times from the attached calendar, and books one after the read-back and
  a yes, with one clarification for an unclear answer and a new read-back for
  any change.

Each tool step in them runs only once the AI agent has that tool; until then
it takes its error route. A template does not change a draft you already have.

### Engines and tests

- **Cascade** says each line with its results exactly as written. **GPT-Live
  1** is given each line, results filled in, to read exactly, and says it in
  its own voice; its words are not guaranteed to match. Gemini Live cannot run
  workflow calls.
- **Bookings follow the same rule on every engine**, GPT-Live included, as
  for an AI agent without a workflow: the engine speaks the platform's
  read-back line, the caller's explicit answer is taken as a yes, a no, a
  change or unclear (with the one clarification), and only a yes books exactly
  the details read back. The calendar's own checks are unchanged.
- Outbound calls, an inbound call from a caller you armed a **Phone** test for,
  and the **Talk** test run tool steps the same way, with the AI agent's real
  tools. Talk is a browser test, so its booking writes only to a calendar
  connection set up for test bookings; see
  [Calendar booking](/docs/calendar-booking#test-without-accidental-appointments).
- **Chat** calls no real tool. A step whose tool the AI agent has not
  configured fails as it would on a call (`tool_not_configured`): no knowledge
  base with a ready document is attached, or the tool is not in the AI agent's
  tools. Every other tool step succeeds with clearly synthetic values
  (`test-knowledge_answer`, `test-available_times`), and a booking step goes
  through the read-back question and books nothing.

### What a tool step never runs

- **On a call that holds a protected value.** Such a call runs no tool, so its
  tool steps take their error routes. The agent page's
  [What runs on calls](/docs/what-runs-on-calls) shows **Protected values** for
  the AI agent's tools while the published workflow declares one.
- **Webhook tools.** They have no read or write kind yet, so a workflow cannot
  use them.
- **Send an SMS, transfers, callbacks, call outcomes and ending the call.** A
  workflow has its own **Send SMS**, **Transfer**, **Outcome** and **End**
  steps for these, and validation refuses declaring the AI agent's built-ins
  for them (`UNKNOWN_AGENT_TOOL`).

A workflow's tool results are kept with the call's transcript and deleted with
it, when the call's recording is deleted or its retention period ends.

## Runtime guarantees

The compiled contract enforces, server-side, on every turn:

- only the active step, its allowed routes, and approved context reach the
  model;
- the model's structured decision is validated before anything executes;
- only the tool the active step declares may run, and the AI agent's model is
  offered none; the one write, a calendar booking, runs only after the
  caller's yes to the platform's read-back;
- a protected value leaves the server only after the caller's confirmation is
  stored, and only in the lines after it;
- per-step visit counts, a total turn budget, and a per-turn timeout are hard
  limits;
- unknown routes, malformed decisions, missing capabilities, and exhausted
  budgets fail closed with a spoken, localized farewell rather than an open
  line.

The workflow API — drafts, publishing, versions, runs, simulations, and phone
pins — is part of the [REST reference](/docs/api-reference).
