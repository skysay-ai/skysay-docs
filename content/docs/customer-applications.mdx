Use a customer application when your system owns the changing business record
and wants Skysay to run the phone conversation. Your application selects
the case and recipient, calls the API, answers approved live-data requests
through [Integrations](/docs/integrations), and reconciles signed results.
Skysay owns the governed call execution.

## Ownership boundary

| Your application owns | Skysay owns |
| --- | --- |
| Recipients, cases, current balances, call cadence, retries, and final business outcomes | Policy- and wallet-gated call execution, managed agent runtime, tool allowlist, recordings/transcripts, and call results |
| CRM, calendar, billing, database, correct-person policy, and business idempotency | Phone number/media operation and Skysay authorization boundaries |
| Live data through an Integration Action | Stable private reference material through a Knowledge Base |

The hosted agent is managed in Skysay. Its AI model can be Gemini or another
supported model. The model decides whether to use an allowed read Action; it
does not receive your application's credentials or authority to choose arbitrary
URLs.

```mermaid
sequenceDiagram
  participant App as Your application
  participant OP as Skysay
  participant Agent as Hosted agent
  participant Adapter as Your Integration adapter
  participant System as CRM or billing system

  App->>OP: POST /v1/calls with durable case reference
  OP->>Agent: policy-gated managed call
  Agent->>OP: request attached read Action
  OP->>Adapter: signed typed JSON request
  Adapter->>System: authorize and read current fact
  System-->>Adapter: safe projection
  Adapter-->>OP: schema-valid JSON result
  OP-->>Agent: bounded result
  OP-->>App: signed lifecycle and artifact events
```

## Start one call

Use `POST /v1/calls`. Supply `Idempotency-Key` for retries; it is preferred over
the optional `idempotency_key` body field. The [generated API
reference](/docs/api-reference) contains the exact current schema.

```bash
curl -X POST https://api.skysay.ai/v1/calls \
  -H "Authorization: Bearer $SKYSAY_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: reminder-case-456-attempt-1" \
  -d '{
    "project_id": "proj_123",
    "from_phone_number_id": "num_123",
    "to_phone_number": "+1 555 0100",
    "country": "US",
    "purpose": "payment_reminder",
    "agent_id": "agent_123",
    "user_authorization": {
      "authorized_by": "ops-user-123",
      "reason": "customer-approved payment reminder"
    },
    "external_reference": "case_456",
    "external_group_reference": "reminder_batch_2026_08",
    "call_context": { "locale": "en-US" }
  }'
```

`country` is optional. Skysay derives the destination country from
`to_phone_number`'s calling code; a `country` you send is used only when the
number cannot be attributed to a country, and never overrides it.

`external_reference` is your stable case ID; Skysay stores it but does not
interpret it. `external_group_reference` can identify your batch. Keep
`call_context` small and non-secret—at most 32 JSON properties—and use it only
for facts valid when the call begins. It is not a place for case history,
credentials, or authorization tokens. A conversation workflow's read tool is the
one thing served from it: send the fields that tool projects under
`call_context.case_snapshot`. See [Agent workflows](/docs/agent-workflows).

For a hosted agent with published language profiles, select one with
`runtime_config.language` in the call request. A `locale` or
`preferred_language` property inside `call_context` is only metadata and does
not select a profile. Your application still owns row overrides and batch
language choices. See [Multilingual outbound
calls](/docs/multilingual-outbound) for configuration and admission behavior.

### An agent that could not take the call is refused before anything is spent

If the selected agent's published voice setup is one the voice agent could not
build a call from—no instructions, no exact voice, no greeting where one is
required, or a component that cannot run the call's language—`POST /v1/calls`
answers `400`:

```json
{
  "error": "realtime_config_not_runnable",
  "reason": "system_prompt_missing",
  "blockers": [{ "code": "system_prompt_missing", "scope": "agent", "detail": "" }]
}
```

No call is created, no wallet balance is reserved, and no origination job is
queued, so retrying after fixing the agent is an ordinary new request. The codes
are the same ones the workspace shows for that agent, so the remedy is the one
already named there. Previously such a request was accepted and the call ended
before it had any audio.

For a multilingual agent the check covers every published language, not only the
one this call speaks: with [Follow the caller](/docs/multilingual-outbound), the
voice agent prepares all of them before the call connects, so each blocker's
`detail` carries the language it belongs to.

A campaign whose agent is in this state finishes each contact as
`agent_not_runnable` rather than dialling it.

### Retry, backpressure, and cancel boundaries

- Repeating the same canonical request with the same idempotency key returns the
  original call. Reusing a key for a different request returns `409`.
- A full bounded outbound queue returns `429` with `Retry-After` and
  `retry_after_seconds`. Respect that delay and keep your own queue bounded.
- `POST /v1/calls/{call_id}/cancel` can cancel a queued call whose originate
  job has not been claimed, and it releases the corresponding wallet
  reservation. It can also cancel a call held for review (`needs_review`),
  which never reserved anything. Once a worker has claimed the job, the API
  returns `409` rather than pretending a carrier call was stopped.

- `POST /v1/calls/cancel-batch` with `{"external_group_reference": "...",
  "project_id": "..."}` cancels every call of that batch that has not been
  dialled yet (queued, held by the live-call gate, or held for review), through
  the same path as the single-call cancel, so each reservation is released and
  each call gets its `call.canceled` event. It handles up to 100 calls per
  request and answers `{canceled, in_progress, campaign_owned, has_more}`:
  repeat it until `has_more` is false. Calls already ringing or live finish
  normally (`in_progress`). It never cancels a campaign's calls: a reference
  that is one of your campaign ids is refused with `409`, so pause or cancel the
  campaign instead.

### Calling hours on a direct call

A call or an SMS can carry its own calling window, so your application cannot
reach someone at three in the morning by mistake:

```json
"calling_window": {
  "windows": {"monday": [{"start": "09:00", "end": "18:00"}], "tuesday": [{"start": "09:00", "end": "18:00"}]},
  "time_zone": "Europe/Tallinn"
}
```

`windows` uses the same shape as a campaign's calling windows. The time zone is
the one you name; without one, the destination number's own zone when the
number has exactly one; otherwise `fallback_time_zone`; if none of these
applies (for example a US number spanning several zones) the request is refused
with `400`. Outside the window, `POST /v1/calls` and `POST /v1/messages` answer
`409` with `error: "outside_calling_window"`, `next_window_opens_at`, the
`time_zone` used, and a `Retry-After` header; nothing is created or reserved, so
retrying with the same `Idempotency-Key` once the window opens places the call.
A call admitted inside its window is checked again just before it dials and is
refused if the window has closed meanwhile; a call already answered is never
cut off by it. The call resource shows the window it was placed under as
`calling_window` (with `time_zone_source`: `explicit`, `destination` or
`fallback`). Campaigns keep their own calling windows. Inbound calls are not
affected.

Read current progress with `GET /v1/calls`, and fetch recording, transcript,
waveform, and artifact evidence through the call endpoints in the generated
reference. Use [signed events](/docs/post-call-results) for prompt,
authoritative reconciliation rather than assuming an HTTP create response means
the call completed.

## Live facts come from typed Actions

Attach only the read Actions that this agent needs. At call time the model can
supply only that Action's declared business arguments. Skysay injects the
canonical organization, project, call, agent, external references, and call
context; it signs the request to your adapter. Your adapter verifies the
signature, checks its own business authorization, dispatches `tool.name`, and
returns a bounded response matching the Action's output schema.

This is deliberately different from a Knowledge Base:

| Use | Put it here |
| --- | --- |
| Opening hours, product terms, policy wording, and durable FAQ text | Knowledge Base |
| Current account balance, booking availability, order status, or CRM record | Integration Action |
| A conversation decision or generated wording | The managed model, within the agent's instructions and allowed tools |

## Payment reminder example

A payment reminder is a useful boundary test because the business facts change
and the conversation is sensitive.

1. Your application selects a permitted case and recipient under its own
   cadence, suppression, dispute, time-window, and retry rules. It creates a
   bounded call with an `external_reference` such as `case_456`.
2. Skysay independently authorizes the requested call under its policy,
   wallet, and organization controls, then runs the configured managed agent.
3. Stable explanation of your payment policy can live in a Knowledge Base.
   Account status and payment link must be requested through a narrow read
   Action, never copied into the prompt. The figures a conversation workflow is
   allowed to disclose travel as that call's own
   `call_context.case_snapshot`, bounded by the tool's declared projection.
4. Before your application has established the correct person, its adapter
   returns a safe projection with no balance, debt, or account history. The
   hosted agent must not disclose those facts merely because the caller supplied
   an identifier.
5. Your application receives signed terminal and artifact-ready events, reads
   the evidence it needs, and determines its own next business step. Advisory
   extraction can assist triage but cannot be the accounting or policy record.

Skysay does not replace your CRM, debt/case system, consent process, or
correct-person verification. It provides the governed telephony and managed
agent layer around the call.

## Build for reconciliation

Persist your own case ID, the returned Skysay call ID, idempotency key, and
the final event ID. Deduplicate signed events by their event `id`; deliveries
are retryable. Treat terminal lifecycle events and call evidence as authoritative
for the Skysay outcome. Treat your own case state as authoritative for your
business outcome.

For a compact, schema-validated summary after a completed call, configure
[post-call extraction](/docs/post-call-results). It is optional and advisory;
it never changes the call, policy, wallet, or customer systems.
