title: Policy & outbound
description: How policy-gated outbound works — evaluate first, authorize, then place. Blocked categories and the broker example.

Live outbound calls and SMS never leave the machine unchecked. OpenPhonex makes
the agent **evaluate policy first**, surface the decision and cost, and only then
authorize and place. Scopes fail closed, and the policy engine blocks whole
categories of outbound regardless of scope.

## Request your outbound permit in the workspace

Every workspace needs an approved **outbound permit** before outbound calls or
SMS can authorize — `authorize_outbound` checks it on every attempt. Request
and track it from the **Onboarding** page in the workspace; no API call or MCP
tool is required, though the REST routes and their MCP equivalents cover the
same flow programmatically:

| Operation | Scope | What it does |
| --- | --- | --- |
| `GET /v1/organizations/{organization_id}/outbound-permit` | `onboarding:read` | The stored permit, the profiles you may select from, and live usage against the permit's caps. |
| `POST /v1/organizations/{organization_id}/outbound-permit` | `onboarding:write` | Request or replace the permit. `profiles` and `countries` are both required. |
| `POST /v1/organizations/{organization_id}/outbound-permit/accept-policy` | `onboarding:write` | Record acceptance of a policy version without changing what the permit authorizes. |

Over MCP the same two operations are `get_outbound_permit` and
`request_outbound_permit`. Exact request and response shapes are in the
[API reference](/docs/api-reference).

<Steps>

<Step>

### Finish business verification

Submit your business details on the Onboarding page and wait for operator
approval. You can still fill in the permit request while this is pending — it
queues for review as soon as verification finishes.

</Step>

<Step>

### Choose profiles, channels, and countries

Pick one or more use-case profiles (personal assistant, business support,
appointments, payment reminders, internal operations, customer outreach
campaigns, or a custom implementation-services profile), the channels you need
(voice, SMS, or both), and the destination countries. Countries default to
wherever your workspace already has numbers.

**At least one destination country is required.** A request with no countries —
or with only values that do not normalize to a two-letter code, such as a
country name, a three-letter code or an empty string — is refused with
`400 select at least one destination country`, and nothing is written: an
already approved permit keeps exactly the countries it had. This is not a
formality. `authorize_outbound` only compares a call's destination against the
permit when the permit lists countries at all, so a permit stored with an empty
list would authorize every destination that is not on the sanctions block —
the opposite of what choosing countries is for. A permit with no country
restriction is something only an OpenPhonex operator can approve.

What is checked is the **shape** of each value, not membership of the assigned
ISO 3166-1 list. The picker offers regions that have no calling code, and the
API accepts aliases such as `UAE`, `USA` and `UK`, so a list checked against
assigned codes would refuse selections the workspace itself offers. A
well-formed but unassigned code such as `ZZ` is therefore stored exactly as you
sent it — and then matches nothing, because a call's country is derived from
the number dialled. Such a permit fails closed: every call is held for review
rather than authorized. Read the countries back from
`GET /v1/organizations/{organization_id}/outbound-permit` and check they are the
ones you meant.

</Step>

<Step>

### Accept the outbound policy

Accept the current outbound policy version before submitting.

</Step>

</Steps>

The result depends on your workspace's state:

| Status | Meaning |
| --- | --- |
| Not requested | No permit has been submitted yet. |
| Pending review | A standard profile was requested before business verification finished, or a custom (implementation-services) profile was selected — an OpenPhonex operator reviews it. |
| Approved | Outbound is active immediately within the approved profiles, channels, countries, and caps. |
| Suspended | An operator paused outbound for this workspace. |

<Callout type="warn" title="Re-requesting an approved permit">
  Submitting a new request replaces the currently approved permit rather than
  adding to it. Adding the custom implementation-services profile always
  requires a new review, which can pause outbound until it is approved again.
</Callout>

## The outbound sequence

<Steps>

<Step>

### Evaluate

```text
→ evaluate_outbound_policy(...)   # policy:evaluate
```

Returns the policy decision and cost estimate **before** anything leaves the
machine. This is a read — it changes nothing.

</Step>

<Step>

### Get explicit human approval

Show the decision and cost to a human and wait for a clear yes. Never place a
live call or send a live SMS on an implied approval.

</Step>

<Step>

### Authorize and place

```text
→ authorize_outbound(...)    # policy:evaluate
→ create_outbound_call(...)  # calls:write
```

</Step>

</Steps>

## Self-hosted gateways use the same gate

A self-hosted gateway in `local` outbound mode does not call
`create_outbound_call`; it calls
`POST /v1/gateway-deployments/{gateway_id}/outbound-calls` with its own
deployment-bound token. That route runs the identical admission — the same
`authorize_outbound` decision, the same kill switches and caps, the same wallet
reserve — and only then mints the single-use authorization the host needs to
reach media. A blocked decision returns `authorized: false` with no
authorization, and the call is recorded as `policy_blocked` exactly as it would
be for a remote request. See [Deployment modes](/docs/deployment-modes) for how
a deployment chooses its originator.

## Blocked categories

The policy engine blocks outbound in these categories regardless of scope:
healthcare, political, emergency, robocalling, mass outreach, telemarketing,
lead generation, scraped / listed-contact broker campaigns, spoofing, and cold
sales. Debt collection is not category-blocked — it is permitted subject to
per-customer onboarding approval and the acceptable-use policy.

<Callout type="warn" title="Broker example">
  A Czech contact-broker campaign that dials a purchased list is a
  scraped/listed-contact broker category — `evaluate_outbound_policy` returns a
  blocked decision, and `create_outbound_call` fails closed. The agent should
  report the block and stop, not retry.
</Callout>
