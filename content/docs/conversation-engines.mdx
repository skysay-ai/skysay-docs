A hosted Skysay AI agent answers the phone with one **conversation engine**.
The default is **Standard**: speech-to-text, a model, then text-to-speech. You
can instead choose **GPT-Live 1**, which listens and speaks at the same time.

Telephony still uses Skysay numbers and LiveKit. GPT-Live 1 does not send
the call to OpenAI SIP.

## Choose the engine

In the workspace, open the AI agent and look at **Voice**. The first control is
**Conversation engine**. The same choice is the first control on the create
wizard's voice step.

- **Standard** keeps separate transcriber, model, and voice rows. Interruptions,
  acknowledgements, and tool-wait speech stay under your control.
- **GPT-Live 1** replaces those three rows with a GPT-Live voice and a backend
  model for tools. The live model owns barge-in, backchannels, and waiting
  speech, so acknowledgements and turn-taking stay off for that engine.

`GET /v1/agent-catalog` lists both engines under `conversation_engines`.
Standard remains the default when you omit the field. Each row declares what
the engine can do rather than leaving you to infer it from its name; today the
one declared property is `has_language_axis`.

## Engines and the language axis

A **language axis** is the group of three settings that only make sense for an
engine that picks a transcriber and a voice per language: the accepted language
set, the per-language overrides, and **Follow the caller**.

- **Standard** has the axis. `has_language_axis` is `true`.
- **GPT-Live 1** does not. It has no language parameter, no separate
  transcriber, and one voice for the whole call, so `has_language_axis` is
  `false`.

Read the flag from the catalog rather than matching on the engine id. Any
future voice-to-voice engine will declare `false` and follow exactly the same
rule, so a client that reads the flag needs no change when one is added.

## Browser testing

The test panel offers two targets. **Current draft** runs the engine, voice
and backend as they stand on the page, before you publish -- switch a
Standard agent to GPT-Live 1, pick a voice, and talk to it. **Published** runs
the last published snapshot. The panel names what each target will run: for
GPT-Live 1 the voice and engine ("Marin · GPT-Live 1"), the backend for tools,
and that speech-to-text is built into the engine.

Two things to know:

- On an agent with published languages, a **Current draft** test takes the
  voice and engine from the draft and the prompt and greeting from the
  published languages. The panel says so.
- While **Follow the caller** is published for an agent, the panel offers only
  **Published**: the published Follow contract is bound to the published
  transcriber. Publish the voice change to test it.

If a test cannot start because of the agent's setup, the panel lists what
needs fixing in the same words the Agents page uses, with a link to the
section, rather than an error code.

## On the homepage demo

The anonymous homepage demo offers every active agent in the Skysay demo
workspace, whatever its engine. A GPT-Live or Gemini Live agent appears once,
in its own language, and follows the visitor's language inside the session, as
it does on a phone call. It opens with its configured greeting, and the demo's
session length and daily limits apply exactly as they do to a Standard agent.

## API and MCP

The discriminator is `voice_frontend`: `cascade` or `gpt_live`. Omit it and
the agent stays Standard.

An engine whose catalog row says `has_language_axis: false` refuses
`languages`, `language_profiles` and `follow_caller`. Both writers refuse them
-- `POST /v1/agents` and `PATCH /v1/agents/{agent_id}/voice-stack`, over REST
and over MCP -- with a `400` that names the field and the engine:

```text
GPT-Live has no language set; omit languages for this conversation engine
```

The field is refused rather than accepted and ignored, so a client never
believes it chose a set the engine cannot honour. `PATCH /v1/agents/{agent_id}`
has never saved these three fields and still answers `400` pointing at the
voice-stack route.

A language set the agent kept from its Standard days stays stored and is
inert: its profiles are published engine-shaped, no per-language transcriber or
voice override is applied, and Follow the caller publishes disabled. Nothing
clears it on a later save, because it is what a switch back to Standard
resumes -- send `voice_frontend: "cascade"` with a full Standard stack and the
three fields are writable again in the same request.

A browser test's draft overlay (`POST /v1/agents/{agent_id}/browser-sessions`
with `snapshot: "draft"`) names its engine in `draft.stack.voice_frontend` and
carries that engine's own fields: for GPT-Live the `voice` and `model`
(backend), for Standard the `transcriber`, `model` and `voice`. See the
request schema in the API reference.

```json
{
  "voice_frontend": "gpt_live",
  "voice": {
    "provider": "openai",
    "model": "gpt-live-1",
    "voice_id": "marin"
  },
  "model": {
    "provider": "openai",
    "model": "gpt-5.6-luna"
  }
}
```

`POST /v1/agents` and `PATCH /v1/agents/{agent_id}/voice-stack` accept the
field. So do MCP `create_agent` and `set_agent_voice_stack`.

`GET /v1/agents/{agent_id}/voice-stack` always returns `transcriber`, `model`,
and `voice`. For GPT-Live 1 those are an OpenAI compatibility projection:
native captions as the transcriber, the Responses backend as the model, and
`gpt-live-1` with the selected voice id.

Patching a Standard transcriber onto a GPT-Live agent without switching the
engine is refused. Switching back requires `voice_frontend: "cascade"` and a
full Standard stack.

## Voices, language, and opening

GPT-Live 1 offers fourteen voices: Marin, Cedar, Gleam, Meridian, Willow,
Stone, Vesper, Quartz, Ripple, Delta, Cinder, Beacon, Bossa and Tempo. Browse,
compare and audition them in the [Voice Library](/docs/voice-library#openai-gpt-live-1-voices)
under the **OpenAI** provider, or pick one directly on the engine card in the
agent editor. **Use in an AI agent** from the library switches the draft to
GPT-Live 1 and tells you so; nothing is published until you publish.

GPT-Live voices are independent of spoken language. Do not filter them through
Standard text-to-speech tables. The engine follows the caller's language
automatically and cannot be pinned to one; see
[Which languages the voice agent follows](/docs/language-following) for what
that means and how to test your language. Opening language is configurable and
does not lock the rest of the call.

`GET /v1/agent-catalog` lists each voice under `conversation_engines` with
OpenAI's own descriptive fields where the provider documents them:
`presentation`, `regional_influence`, `provider_language_label` (OpenAI's
per-voice Language label, a description rather than a capability), `source`
(Natural or Generated) and `default`. Marin and Cedar carry a presentation
only; OpenAI does not document the other fields for them, and Skysay does
not infer them.

On outbound phone calls without a workflow, GPT-Live 1 and Gemini Live let
the person speak first. They hear the whole pickup before Skysay releases the
first response. A request or correction in the pickup should be answered
first; a simple hello is answered with the configured opening. If nobody
speaks for two seconds, Skysay requests the opening. See
[Who speaks first](/docs/who-speaks-first) for the timing and call types.

The configured opening sets the initial language and script. A per-call opening
from the Calls API replaces the agent's saved opening for that call. These are
instructions to a voice-to-voice model and cannot guarantee exact delivery;
the measured Sinhala limit in
[Which languages the voice agent follows](/docs/language-following) still applies.

If caller input cannot be preserved or observed during startup, the call fails
instead of treating missing audio as silence. Startup audio is retained only
in memory, for at most eight seconds. A reconnect during the pickup also ends
that attempt. This is a universal opening safeguard, with no new API field or
agent-editor setting.

### Calls where the agent speaks first

Inbound phone calls and browser tests keep their existing agent-first opening.
The following input hold and quick-reply recovery apply to that opening path.

While the opening plays, the engine does not hear the line. A voice-to-voice
engine answers whatever it hears, so hold music, an automated announcement or
someone saying "hello?" at the moment the call connects could otherwise get a
reply before the greeting was ever said. Skysay keeps that audio from the
engine until the opening has been spoken: until the engine's own transcript of
what it said covers the opening, and the line has then been quiet for about a
second. Skysay itself keeps listening the whole time, so answer detection and
the call recording are not affected.

On GPT-Live, a quick reply after the greeting stops can arrive while Skysay is
still checking that quiet period. Skysay briefly retains this post-greeting
audio and passes it to the engine once the opening check succeeds, before new
live audio. Silent intervals are not replayed; a recovered reply includes at most
200 milliseconds of leading quiet. Retention is limited to two seconds and stays
in memory. This does not recover words spoken over the audible greeting or establish what the
person meant.

Recovery is skipped when opening delivery cannot be established, the connection
restarts, observation is interrupted, delayed audio arrives in a burst, the
buffer reaches its limit, or the call is ending. Normal listening still resumes under the existing opening rules.
If the caller's reply was not understood, the agent may still need to ask them
to repeat it.

Two consequences to plan for:

- Anything the person on the line says during the opening is not passed to
  the engine afterwards. If they speak over the greeting, the engine answers
  what they say next.
- If the engine does not finish the opening, it starts listening anyway: 12
  seconds after the call is answered if it has said nothing, or at most 6 seconds
  plus a tenth of a second per character of the opening (never more than 30
  seconds) after it started speaking. A call whose engine said something
  other than the configured opening is not counted as having delivered it.

Without an opening message, GPT-Live and Gemini Live write their own
greeting. When the call carries per-call context, that greeting asks for the
person by first name only, or who is speaking when the first name is unclear,
and states no amount, reference or other account detail.

Phone and browser Talk workflow runs cannot use GPT-Live. Skysay rejects
that combination before reserving call funds or dispatching media. Ordinary
GPT-Live calls and text workflow simulations remain available.

## Call evidence

GPT-Live saves native captions and full-call recordings when recording is enabled.
Captions can be imperfect, especially across languages, and for some languages
(Sinhala most often) they can be missing entirely. When the other party spoke
and the engine answered without a caption, the transcript in the Calls
workspace marks it with a "Spoke — no transcript" line; see
[Read call evidence](/docs/read-call-evidence). Per-turn audio clips and
some timing evidence can be incomplete even when the full recording is available.
Check the call's evidence status before using those details to assess audio quality
or response speed.

## Billing

GPT-Live 1 is billed by call duration, from the moment the call is placed, at
**$0.05 per minute**, including silence, plus tokens for the backend that
handles tools. Standard speech-to-text is not charged on that path.

See the [generated API reference](/docs/api-reference) for the exact request
and response shapes.

## When a live agent proposes to end a call

For a live voice model, Skysay waits for the model's goodbye to finish before
closing the connection. Caller input stays open during that wait. If local
speech detection says the caller is already speaking, the model's `end_call`
request is refused. If the caller starts speaking while that close is pending,
Skysay withdraws the close and leaves the conversation open. After the goodbye,
there is up to 750 ms for the caller to take the floor, within the existing
shutdown time limit.

This safeguard is automatic; there is no new agent-editor switch or API field.
It detects speech activity rather than meaning: noise can keep a call open,
and speech the detector misses cannot stop closure. It does not establish
identity, confirm a promise, count clarification questions, undo a goodbye
already heard, or end a call when the model forgets to invoke `end_call`.
Balance limits and other platform-enforced endings still close the call.

On phone and workspace browser-test calls, the existing farewell fallback can
also request closure after it recognizes the caller's closing words. If the
caller takes the floor again, that pending request is withdrawn; a later
goodbye can request a fresh close. A fallback close does not mean the model
invoked `end_call`. Model tool use and actual call disconnection are separate
evidence.
